nemo → pi-like basic agent: upgrade plan

(Excluding a TUI and a bash/exec tool — those are separate work streams.)

What nemo has today

  • Agent loop: OpenAI-compatible streaming client (OpenRouter), tool-call loop (max 32 iterations), session history, system-prompt seeding, history rollback on failed turns
  • Tools: fetch (with readable-extraction), read, write, edit (unique-match text replace), grep, find, ls
  • Robustness: retries with backoff + Retry-After, per-call/run timeouts, byte caps everywhere, UTF-8-safe truncation, redirect/scheme policy, handles both delta and message stream shapes, reasoning/reasoning_content keys
  • UI: plain REPL with [reasoning]/[output]/[tool]/[system] block rendering

The architecture is clean for extension: Tool, Agent, and session are already separated, so everything below bolts on without restructuring.

The gaps

Grouped by theme:

A. Context & memory

This is the biggest hole. History grows unbounded until the provider 400s with “context length exceeded”, and then the user is stuck (the turn is dropped, nothing shrinks). Sessions live only in memory. The usage field in the final SSE chunk is parsed but discarded.

B. Workspace grounding

grep/find walk everything: no .gitignore awareness, so the first search in a repo with node_modules/ or vendor/ drowns in noise. No AGENTS.md-style project instructions. The system prompt is static — no cwd, platform, date. read returns raw text without line numbers or file stats, which makes anchoring edits and navigating big files harder for the model.

C. Safety & trust

write/edit execute silently: no approval gate, no diff preview. fetch checks scheme but doesn’t block private IPs/localhost (SSRF if the model fetches attacker-influenced URLs).

D. Operability

Model and endpoint are hardcoded (one env var for the key). Ctrl+C kills the whole process instead of aborting the turn. No one-shot -p mode, no /commands, no transcript on disk.

E. Robustness polish

Empty assistant reply is a hard error (could re-ask once); finish_reason: "length" isn’t treated specially; grep will happily match binary files.

Suggested build order

  1. Quick wins: #2 turn-level interrupt (✅ done), #3 config/flags, #5 gitignore (✅ done, root-level only)
  2. Grounding: #7 (✅ done), #8 (✅ done), #6
  3. Accounting & storage: #11 usage tracking (✅ done), #16 JSONL, then #4 resume on top
  4. Compaction: #1 + #17 — hardest to get right (when to trigger, what to summarize, how to preserve tool-call/result pairing in history)
  5. Safety: #9, #10, #19
  6. Ergonomics: #12, #13, then P2 polish

Open design questions

  • Compaction design — summarize-and-replace (pi-style: condense old turns into a summary message) vs. simple sliding-window trim (drop oldest tool results first, keep user/assistant text)? The former preserves intent, the latter is much simpler and tool results are usually the bulk.
  • Approval UX pre-TUI — is a plain y/n stdin prompt acceptable for #9, or should that wait for the TUI and land as a --yes/--dry-run flag instead?
